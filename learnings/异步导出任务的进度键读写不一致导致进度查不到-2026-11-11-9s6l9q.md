# 异步导出任务的进度键读写不一致导致进度查不到

## 背景
dev-problem 的「问题件待退改」列表支持导出。导出为后台异步任务:
接口先写入 `notstart` 状态,任务运行时写入进度,完成后写入下载地址,
前端凭 `code` 轮询进度。进度和结果保存在 Redis 中。

## 症状
- 【已验证】Git 历史显示,修复前列表导出的「写入初始状态」「读取进度」
  与「写入进度、结果」使用的是不同的 Redis key 前缀。
- 【合理推测】前端轮询列表导出进度时,会读不到任务写入的进度和下载地址,
  表现为进度不更新或一直停在未开始。提交中没有现场截图或工单,
  这只是根据代码得出的推测。

## 根因
【已验证,有代码证据】同一个 Service 里定义了两个相近的前缀:
- `exportLocation = 'problem_refund_export_location:'`
- `location = 'problem_refund_list_export_location'`

修复前,列表导出任务把进度和下载地址写入 `exportLocation . $code`,
但初始状态和读取进度的 `getExportListProgress` 使用 `location . $code`。
读写前缀不一致,导致读到的不是任务写入的值。

另外,Controller 的进度接口调用的是 `getProgress`,它读取 `exportLocation`,
对应的是另一类导出,而不是这个列表导出。
【已验证】这一处在同一提交中被改为 `getExportListProgress`。

## 解决方法
【已验证,来自提交 diff】
1. 列表导出任务写进度和结果时改用 `$this->location`,与读取、初始化一致。
2. Controller 的进度接口改调 `getExportListProgress`。
3. 同一提交还把 `is_print = 'all'` 排除出筛选条件,避免它被拼成
   `extend.is_print = 'all'` 而得到空结果。这一项与 Redis key 问题无关。

【已验证】该提交只改了 2 个文件,没有包含测试代码,仓库里也没有 `tests` 目录。
【未确认】提交者是否做过手工验证、结果如何,Git 历史里没有记录。
不能说明修复后已通过测试。

## 适用范围
- 使用 Redis 保存异步任务进度和结果,并由「启动、执行、查询」三处共同读写的功能。
- 同一个类中为不同导出或任务定义了多个 key 前缀的场景。

## 限制条件
- 不适用于不依赖 Redis 的同步导出。
- key 命名、过期时间(此处为 24 小时和 1 小时)需按业务确认。
- 修复前后的线上症状未被确认,不能当作已经复现过的线上故障。
- `location` 前缀本身没有分隔符(`...location` 后直接接 `$code`),
  与 `exportLocation`(以 `:` 结尾)风格不一致。这是观察到的事实,
  但是否有实际影响未确认。

## 建议(推测性的最佳实践,非该提交内容)
- 把读、写、初始化统一用一个常量或方法生成 key,例如 `progressKey($code)`。
- 同一个类里为不同导出分别定义前缀时,在命名上直接体现业务,并写明用途。
- 为「启动、写进度、读进度」增加一个简单的集成测试。
