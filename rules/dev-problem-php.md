# Dev Problem — PHP 开发规范

## 1. 适用范围与总体原则

本规范适用于 `dev-problem` 项目，技术栈为 ThinkPHP 5.0.7、tpadmin、MySQL、Redis 等。

- 规则主要约束新增和修改的代码，不要求一次性整改历史代码。
- 遵守最小改动原则，不修改与当前任务无关的业务逻辑。
- 不擅自升级 PHP、ThinkPHP 或 Composer 依赖。
- 不擅自修改数据库结构、删除文件或改变外部接口行为。
- 历史风险应报告；只有任务明确要求修复时，才在授权范围内修改。
- 优先沿用所在模块已有的目录、调用方式和命名约定。

## 2. PHP 和 ThinkPHP 兼容性

- 生产 PHP 版本尚未确认。在确认前，以 PHP 7.0 作为保守语法兼容下限。
- 不使用 PHP 7.1 及以上或 PHP 8 专有语法与函数。
- 不引入未经确认的框架 API 或第三方依赖。
- 使用 ThinkPHP 5.0.7 项目中实际存在的 API。
- 不直接修改 `vendor/`、`thinkphp/` 中的第三方或框架代码。
- 如果任务必须依赖新版本能力，应先说明风险和迁移条件。

## 3. 模块与分层

- 新增接口应尽量遵循 Controller → Service → Repository/Model 的分层。
- Controller 负责参数处理、验证、认证、授权及响应，不应新增复杂业务处理。
- Service 负责业务逻辑、事务边界及跨模块协调。
- Repository/Model 负责数据访问。
- 修改历史代码时，尊重所在模块现有结构，不因普通需求进行无关的大规模重构。
- 不通过复制整个 Controller 或创建 `*Copy`、`*Two` 等文件作为长期扩展方式。
- 修改超过 2,000 行的历史控制器时，优先评估将新逻辑放入独立 Service，但不得为了满足规则擅自拆分整个控制器。

## 4. SQL 和数据访问

- 新增 SQL 必须使用安全的查询构造器或参数绑定。
- 禁止把用户输入直接拼接到 SQL、Where 条件或原生查询中。
- 表名、列名、排序字段等不能参数绑定的 SQL 标识符必须使用服务端白名单。
- 使用 ThinkPHP 查询构造器时，优先采用明确的数组条件，例如 `Db::name('order')->where(['id' => $id])->find()`。
- 原生 SQL 必须使用当前 ThinkPHP 版本实际支持的参数绑定方式。
- 列表查询应有合理的分页或记录数量限制。
- 避免循环中逐条查询数据库的 N+1 问题。
- 新增查询应考虑索引、数据规模和执行成本，但不得擅自修改数据库结构。

## 5. 凭证、配置和敏感数据

- 不得在代码、注释、测试数据或 Git 提交中新增真实密钥、密码、Token 等凭证。
- 使用项目既有的安全配置读取机制，不硬编码凭证。
- 不提交新的 `.env*` 敏感配置文件。
- 不在日志、异常、接口响应和 AI 总结中输出真实凭证或未经必要脱敏的个人信息。
- 如果发现历史凭证泄露，应报告文件位置、风险及是否需要轮换，不输出凭证值。
- 删除敏感文件并不等于消除 Git 历史中的泄露风险。

## 6. API 认证、授权和参数验证

- 新增或修改 API 必须核对所属模块的认证方式。
- 后台接口遵守既有 Session/RBAC 权限机制。
- API v2 遵守已有 Token 验证和接口方法授权机制。
- 对用户可访问的网点、组织和业务数据进行对象级授权检查，防止越权读取或修改。
- 新增外部输入应通过项目现有的 Validate 机制验证类型、长度、格式和范围。
- 不直接信任 `$_GET`、`$_POST`、`$_REQUEST` 等原始输入。
- 使用项目已有的异常体系和 ErrorCode。
- 不向客户端返回数据库错误、敏感内部路径或堆栈。

## 7. 事务与数据一致性

- 涉及多表、多连接或多个系统的写入时，必须分析事务和一致性边界。
- 显式事务应覆盖正确的数据库连接，并在异常时进行必要回滚。
- 不使用空 `catch` 隐藏写入失败。
- 避免在数据库事务中执行不可控的长时间外部调用。
- 将 Kafka、Redis、Elasticsearch 或 HTTP 副作用放到 Commit 后，并不自动保证跨系统一致性。
- 对需要可靠交付的事件，评估 Outbox、幂等重试、补偿或对账机制。
- 不得自行承诺严格一致性；无法确认时说明潜在失败窗口。

## 8. Redis、队列和常驻任务

- Redis Key 应使用业务命名空间，明确生命周期及是否需要 TTL。
- 缓存需要考虑失效策略和数据一致性。
- 队列消费者应考虑重复投递、幂等处理、重试上限和异常消息处理。
- 外部调用必须评估超时和失败恢复。
- 常驻任务应避免无休眠的高频死循环，并具备合理的日志、资源释放和停止机制。
- 不得擅自更改已有任务调度频率、队列确认语义和生产运行参数。

## 9. 调试与代码风格

- 不提交用于调试的 `var_dump`、`print_r`、`dd`、`die`、`exit` 或 `phpinfo`。
- 日志优先沿用项目现有的 ThinkPHP 日志机制。
- 日志不得包含真实凭证或敏感业务数据。
- 新代码保持清楚、一致、兼容当前 PHP 版本的风格。
- 不为格式整理而大规模修改无关历史代码。
- 注释应重点解释业务原因、边界条件和非显而易见的设计决策。

## 10. 修改完成后的汇报

完成开发任务后，必须说明：

1. **修改内容**：具体文件、主要方法和行为变化。
2. **兼容性风险**：PHP、ThinkPHP、数据库、Redis、外部依赖。
3. **实际验证**：执行的命令、测试结果和检查范围。
4. **未验证事项**：没有 PHP 环境或无法运行测试时，明确说明。
5. **发现的历史风险**：与当前任务无关的问题单独列出，不擅自扩大修改范围。

禁止将未经执行的测试描述为已通过。
